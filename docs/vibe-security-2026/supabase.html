Top 4 Pre-Launch Risks in Supabase RLS Production Apps

1. Tables Created Without ENABLE ROW LEVEL SECURITY

PostgreSQL tables created in the SQL Editor or AI migrations default to RLS disabled. Anyone who reads your public anon key from browser JS can query PostgREST directly.

2. Leaked service_role JWTs (Bypasses ALL RLS)

VibeShield decodes every Supabase JWT detected in your client bundles locally and immediately raises a Critical alert if the role claim is service_role or an sb_secret_ token.

3. Permissive USING (true) Write Policies

Even with RLS enabled, a quick prototype policy like FOR ALL USING (true) allows any visitor to overwrite or delete other users' records.

4. Public Storage Buckets & Unchecked Grants

Audit public storage buckets and run REVOKE ALL ON ALL TABLES IN SCHEMA public FROM anon so newly added internal tables stay locked by default.

Two-Query Supabase Pre-Launch RLS Audit (Run in SQL Editor)

-- 1. Find any table in public schema with RLS DISABLED (goal: 0 rows)
SELECT schemaname, tablename, rowsecurity
FROM pg_tables
WHERE schemaname = 'public' AND rowsecurity = false
ORDER BY tablename;

-- 2. Find tables with RLS enabled but 0 policies
SELECT t.tablename, COUNT(p.policyname) AS policy_count
FROM pg_tables t
LEFT JOIN pg_policies p ON p.schemaname = t.schemaname AND p.tablename = t.tablename
WHERE t.schemaname = 'public' AND t.rowsecurity = true
GROUP BY t.tablename
ORDER BY policy_count ASC;

Top 4 Pre-Launch Risks in Lovable Production Apps

1. Public Supabase Tables Missing RLS

When Lovable generates a new migration table, forgetting ALTER TABLE ... ENABLE ROW LEVEL SECURITY lets anyone holding the public anon key query or mutate user rows directly via PostgREST.

2. Client-Side Secret Leaks via VITE_* Variables

Any environment variable prefixed with VITE_ is compiled verbatim into public browser bundles. Stripe live keys, OpenAI/Gemini keys, and Supabase service_role tokens must stay strictly inside Supabase Edge Functions.

3. Missing Security Headers on Custom Domains

In our 55-app empirical benchmark, 74.5% of freshly launched AI apps shipped missing 8–9 of 10 Mozilla Observatory headers (CSP, X-Frame-Options, Permissions-Policy, COOP/CORP).

4. Unprotected Storage Buckets & Profile Updates

Public upload buckets and broad USING (true) policies allow unauthenticated users to enumerate files or escalate their own role/plan columns from the browser console.

Copy-Paste Supabase RLS Lockdown + Audit Query for Lovable Apps

-- Step 1: Catch every public table missing Row Level Security (must return 0 rows)
SELECT schemaname, tablename, rowsecurity
FROM pg_tables
WHERE schemaname = 'public' AND rowsecurity = false;

-- Step 2: Enforce per-user isolation on every user-owned table
ALTER TABLE public.profiles ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users read own profile"
  ON public.profiles FOR SELECT TO authenticated
  USING (auth.uid() = id);

CREATE POLICY "Users update own profile"
  ON public.profiles FOR UPDATE TO authenticated
  USING (auth.uid() = id) WITH CHECK (auth.uid() = id);
